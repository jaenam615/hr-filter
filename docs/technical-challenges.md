# hr-filter — 기술적 도전과 설계 결정

AI 기반 서류 심사 필터링 시스템. 채용 공고와 지원자 이력서를 LLM으로 비교 평가해
통과/보류/탈락 판정과 근거를 산출한다. 단순 기능 구현이 아니라, **무엇을 만들고
무엇을 미루며, 어떤 트레이드오프를 택했는지**를 중심으로 정리한다.

**스택**: Kotlin · Spring Boot 3.4 · Exposed(코틀린 SQL DSL) · PostgreSQL · Anthropic Message Batches API · AWS S3 / MinIO · Thymeleaf · Gradle 멀티모듈(14)

---

## 1. "조립을 코드로 강제한다" — 헥사고날 + 명시적 빈 등록 아키텍처

**맥락.** 도메인 로직이 특정 프레임워크·외부 SDK(파서, S3, LLM, 알림)에 묶이면
교체·테스트·확장이 어려워진다. 동시에 `@ComponentScan` 기반 자동 발견은 편하지만,
"어떤 빈이 어디서 왜 등록되는가"가 암묵적이라 규모가 커질수록 추적이 힘들다.

**결정.**
- **포트 & 어댑터**: `infrastructure` 모듈은 **Out-Port 인터페이스만**(구현 0줄) — Repository·Storage·Parser·LLM·Notifier 8종. 구현체(Tika/S3/Anthropic/Slack…)는 각 어댑터 모듈에 격리.
- **컴포넌트 스캔 폐기**: 모든 빈을 `@AutoConfiguration` 클래스의 `@Bean`으로 **명시 등록**. 어떤 빈이 어떤 모듈에서 조립되는지 한눈에 보인다.
- **컴파일타임 의존성 방향 강제**: 14개 Gradle 모듈의 의존 그래프로 레이어 규칙을 *컴파일 단계에서* 강제. 예) `api` 모듈은 `repository-exposed`를 직접 참조 불가 — 반드시 `service`를 경유해야 빌드된다. 규약이 문서가 아니라 빌드 실패로 강제된다.
- **Build Recipe 컨벤션**: 각 모듈의 `type=`(예: `kotlin-boot-mvc-application`)을 읽어 플러그인·공통 의존성을 자동 적용하는 관례 8종을 루트 빌드에 정의. 모듈 빌드 스크립트는 대개 `dependencies {}` 한 블록으로 끝난다.

**결과.** 외부 의존성을 도메인 바깥 경계로 밀어내, LLM 어댑터를 목으로 갈아끼우거나
알림 채널을 설정 한 줄로 바꾸는 게 가능해졌다. 모듈 경계가 곧 아키텍처 문서다.

## 2. 동기 호출이 아니라 비동기 배치 — 비용·처리량 우선 설계

**맥락.** 이력서 평가는 LLM 호출이다. 가장 쉬운 길은 업로드 즉시 동기 호출이지만,
대량 채용 시즌에 수백~수천 건을 실시간 호출하면 비용과 레이트리밋이 곧바로 병목이 된다.
서류 심사는 본질적으로 **지연 허용(latency-tolerant)** 업무다 — 1초 안에 답이 필요하지 않다.

**결정.** **Anthropic Message Batches API**를 채택해 평가를 비동기 배치로 처리.
- 동기 대비 **토큰 비용 50% 절감**, 대량 요청을 단일 배치로 제출.
- 스케줄러가 하루 2회(오전 8시·오후 2시) 신규 이력서를 모아 한 번에 제출 → 결과 폴링 → 저장 → 요약 알림.
- 도메인은 `submitBatch(jobs): BatchHandle` / `pollResults(handle): BatchResults`라는 **공급자 중립 포트**로만 LLM과 대화한다. 폴링·상태머신(`IN_PROGRESS/COMPLETED/FAILED`) 같은 배치 메커니즘은 어댑터 내부에 숨겼다.

**트레이드오프.** 실시간 피드백을 포기하는 대신 비용·처리량·운영 단순성을 얻었다.
이 트레이드오프가 정당한 이유는 "서류 심사는 즉시성이 필요 없다"는 **도메인 특성**에 근거한다.

## 3. LLM 출력을 신뢰 가능한 데이터로 — 구조화 출력 강제

**맥락.** LLM 응답을 자유 텍스트로 받아 정규식·문자열 파싱으로 점수를 뽑아내면,
모델이 말투를 조금만 바꿔도 파싱이 깨진다. 평가 결과가 DB에 그대로 적재되는 파이프라인에서
이 취약성은 치명적이다.

**결정.** 각 배치 요청에 **`output_config.format`(JSON Schema)** 을 실어
응답 구조(`verdict` enum, `score`, 세부 점수 `breakdown`, `reasoning`)를 **API 레벨에서 강제**.
파서는 "잘 짜인 자연어 추측"이 아니라 스키마가 보장된 JSON만 역직렬화한다.

**결과.** 모델 출력 변동에 대한 파싱 취약성을 제거. 신규/실패/만료 항목을 구분하는
배치 결과 처리도 명시적 상태로 다룬다.

## 4. 동시성 안전한 집계 — 애플리케이션이 아닌 DB에서 증분

**맥락.** 배치가 결과를 저장할 때 `batch_run`의 통과/보류/탈락 카운터를 증가시킨다.
"읽어서 +1 해서 다시 쓰기"를 애플리케이션 코드로 하면, 동시 처리 시 lost update가 발생한다.

**결정.** Exposed의 SQL 표현식을 써서 **DB 레벨 원자 증분**으로 처리.
```kotlin
BatchRunTable.update({ BatchRunTable.id eq identity.batchRunId }) {
    it[evaluatedCount] = evaluatedCount + intLiteral(1)   // read-modify-write가 DB에서 일어남
    when (verdict) { PASS -> it[passedCount] = passedCount + intLiteral(1); ... }
}
```
read-modify-write가 애플리케이션 메모리가 아니라 단일 SQL `UPDATE` 안에서 일어나
경합 조건 없이 정확하다.

**그 외 영속성 결정.** 평가 세부 점수는 컬럼 폭증 대신 **PostgreSQL JSONB**(`breakdown`)로
저장 + Jackson 매핑 — 평가 항목이 늘어도 스키마 마이그레이션 없이 흡수. 페이징은
`ORDER BY ... DESC LIMIT/OFFSET`로 대시보드 히스토리 대비.

## 5. 어댑터 경계에서의 실용적 결정들

- **교체 가능한 알림 채널**: Slack / Teams / Email 세 어댑터를 모두 구현하고
  `@ConditionalOnProperty(hrfilter.notifier.channel)`로 런타임 선택. 운영 환경별로 코드 변경 없이 채널 전환.
- **코루틴 ↔ 블로킹 브리지**: AWS SDK for Kotlin은 코루틴 기반인데 Storage 포트는
  블로킹 시그니처다. 어댑터 내부에서 `runBlocking`으로 경계를 흡수해, 도메인에 코루틴을
  누출시키지 않고 포트 계약을 단순하게 유지.
- **로컬-프로덕션 환경 패리티**: 운영의 S3를 로컬에선 **MinIO**(S3 호환)로,
  `docker-compose`로 Postgres+MinIO+버킷 초기화까지 일괄 기동. path-style 접근 등
  S3 호환 차이를 어댑터 설정으로 흡수해 코드는 동일하게 동작.
- **재현 가능한 빌드**: Gradle **JDK toolchain을 21로 고정**해, 빌드를 띄운 JVM과
  무관하게 컴파일·실행 JVM을 통일(버전 불일치로 인한 `UnsupportedClassVersionError` 차단).

## 6. 사용자 경험 — 사람이 개입하는 심사 루프

서류 심사는 완전 자동화 대상이 아니라 **사람의 최종 판단을 돕는** 도구다. 이를 UX로 반영:
- **요약 알림**: 배치 완료 시 개별 건이 아니라 *집계*(평가 N건 · 통과/보류/탈락 요약 + 대시보드 링크)를 한 번에 통지 — 알림 피로 없이 "지금 봐야 할지"를 즉시 판단.
- **대시보드(Thymeleaf)**: 판정·점수·근거를 한 화면에서 검토. 판정별 색상으로 스캔 가능성을 높이고, 같은 화면의 업로드 폼으로 이력서를 직접 투입(human-in-the-loop).

---

## 7. 테스트 전략 — 포트 모킹 기반 단위 테스트 우선

외부 서비스(DB/S3/LLM) 없이 빠르게 도는 단위 테스트를 우선했다.
- 배치 오케스트레이션 서비스는 **8개 Out-Port를 전부 목(MockK)으로 대체**해,
  "이력서 없음 → 무동작", "정상 흐름 → 저장·알림", "LLM 실패 → FAILED 처리",
  "예외 → FAILED + 전파" 같은 **제어 흐름**을 외부 의존성 없이 검증.
- in-process로 도는 어댑터(Tika 파서)와 순수 함수(알림 메시지 포매팅)는 그 자체로 단위 테스트.
- Kotest `DescribeSpec`으로 행위를 문장처럼 기술.

---

## 8. 의도적으로 미룬 것들 — 스코프 판단

좋은 설계는 무엇을 *안 만드는지*에서도 드러난다. MVP 범위에서 다음을 명시적으로 제외하고,
도입 트리거를 문서화했다.
- **벡터 DB / 사전 필터링**: 비용·검색 니즈가 실제로 생기기 전엔 과설계. 트리거가 오면 추가.
- **이벤트 드리븐(큐/이벤트 버스)**: ATS 연동, 평가 결과 컨슈머 3개 이상, 실시간 알림,
  지원자 상태 UX 중 하나라도 필요해질 때 도입. 지금은 도메인이 하나라 모듈식 모놀리스로 충분.
- **이미지/스캔 PDF OCR**: 텍스트 기반 문서(PDF/DOCX 등)로 범위 한정.

---

### 요약

이 프로젝트의 핵심은 *기능을 구현했다*가 아니라, **경계를 어디에 그었는가**다 —
도메인과 외부 세계 사이의 포트 경계, 동기와 비동기 사이의 처리 모델 경계,
지금 만들 것과 나중에 만들 것 사이의 스코프 경계. 각 경계는 도메인 특성(지연 허용,
사람 개입, 단일 도메인)과 운영 현실(LLM 비용, 동시성, 환경 패리티)에 근거한 트레이드오프의 결과다.
